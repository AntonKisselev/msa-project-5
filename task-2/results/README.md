## Выбор технологического решения

### Краткое обоснование - выбор решения пал на Apache Airflow по нескольким причинам:

1. в команде нет опыта использования инструмента для пакетной обработки и компетенция не является, в данном случае,
   фактором
2. исходя из 1 пункта, в команде есть желание изучить именно Apache Airflow, как продукта с большим заделом. Что
   скажется на мотивации и соответстввенно результативности команды
3. на текущем этапе продукт не является излишни избыточен, как альтернативу можно было бы использовать простой cron, но
   airflow решает тоже эту задачу при не сильно бОльших затратах
4. даже на текущем этапе есть большая вероятность, что придется распределять некоторые этапы, например "извлечение
   client_prices" на batch порции, из-за достаточно большого кол-ва строк, что может вызвать ошибку нехватки памяти.
   Сделать это на cron уже будет намного более затратно, нежели на Apache Airflow
5. данное решение легко масштабируется

### Отсутствие опыта и мотивация

Airflow: Изучение Airflow — это инвестиция в универсальный и востребованный инструмент для оркестрации данных. Это
стратегически правильный шаг для команды, который окупится на будущих, более сложных задачах.

K8s CronJob: Изучение "голого" CronJob не дает такого же задела на будущее. Это тактическое решение, которое не
открывает новых возможностей beyond простого запуска по расписанию.

### "Не избыточен" против "простого cron"

Хотя для одной задачи Airflow может показаться "пушкой по воробьям", его стоимость владения ненамного выше, чем настройка и
поддержка надежного cron в K8s.

Ключевое отличие: K8s CronJob гарантирует, что Pod запустится в нужное время. Airflow гарантирует, что весь пайплайн
выполнится от начала до конца с заданной логикой, что гораздо ценнее для бизнеса.

### Потребность в распределенной обработке

Задачу "извлечение client_prices" можно легко разбить на параллельные
подзадачи с помощью Airflow.

Попробовать сделать то же самое на K8s CronJob — это кошмар. Пришлось бы:

Писать отдельный скрипт-планировщик, который создает нужное количество Job'ов в K8s.

Самостоятельно отслеживать завершение всех этих Job'ов.

Писать сложную логику для агрегации результатов и обработки частичных сбоев.

Airflow делает это "из коробки", элегантно и наглядно.

### Легкое масштабирование

Масштабирование пайплайна: Когда появятся новые шаги (например, "валидация цен", "обогащение данными из CRM", "отправка
уведомлений"), в Airflow вы просто добавите новые узлы в DAG, определив их зависимости. В CronJob вам пришлось бы либо
плодить множество отдельных CronJob'ов (и управлять хаосом), либо превратить ваш скрипт в монолитный и сложный для
поддержки.

Масштабирование инфраструктуры: Оба решения отлично масштабируются на уровне инфраструктуры (K8s для CronJob, Celery/K8s
Executor для Airflow). Но Airflow масштабирует еще и логику workflows.

## Итоговый вердикт и рекомендация
***Выбор Apache Airflow*** является не просто допустимым, а стратегически верным по следующим причинам:

Решает сегодняшнюю задачу без "костылей". Да, задача простая, но даже в ней есть нюанс с распределенной обработкой,
который Airflow решает элегантно.

Дает задел на будущее. Следующая задача по обработке данных не потребует выбора нового инструмента — вы просто добавите
новый DAG.

Снижает операционные риски. Встроенные механизмы мониторинга, alerting и повторных попыток делают пайплайн
отказоустойчивым и прозрачным для разработчика.

Соответствует целям команды. Изучение Airflow — это инвестиция в профессиональный рост и повышение эффективности команды
в долгосрочной перспективе.

***Kubernetes CronJob*** стоило бы выбрать только в случае, если:

Задача предельно тривиальна и всегда будет таковой (один скрипт, запускаемый раз в сутки).

Команда уже перегружена и нет ресурсов на изучение нового инструмента.

В инфраструктуре строгий принцип "только K8s" и запрещено развертывать дополнительные сервисы вроде Airflow.

В вашем случае эти условия не выполняются, поэтому Apache Airflow — это обоснованный и правильный выбор.
